# F组正式队员题

## 共同要求

- 保留原有构建可用；提交修改、测试、简短设计说明和运行命令。
- 只修改所选题目涉及的模块，不要求大规模重写。
- 不能把公开样本文件名写成特殊分支；算法组会替换时间顺序、噪声或隐藏样本。
- 最低完成标准是“行为正确、故障可解释、程序不会崩溃”，不是追求复杂模型。

## F1：多车遮挡下的灯条关联与装甲板完整性判断

**比赛情景**：两辆敌方车在哨兵视野中交错，前车底盘会挡住后车的一根灯条。旧程序把所有亮线直接配成装甲板，出现跨车配对和后车被遮挡时仍输出完整装甲板的问题。

**代码入口**：`src/f1_detector.hpp`、`src/f1_baseline.hpp`。

**输入**：`F1_lightbar_candidates.csv` 是主要输入；两个 MP4 只用于回放和可视化。CSV 已经由算法组完成视频解码和基础灯条提取，候选人不需要写 BGR/HSV 分割、灯条检测器或视频读取器。

**要求**：

1. 实现 `ArmorAssociator::associate()`，从匿名灯条候选中给出左右配对。
2. 保留单车场景的基本配对能力，不能把不同车的灯条长期配成一个超宽装甲板。
3. 灯条只有部分可见时，输出 `complete=false` 或低置信度，不能伪造完整装甲板。
4. 提供一个可运行的 CSV 回放程序或测试，输出 `frame,left_index,right_index,complete,confidence`。

**不要求**：重写图像检测、训练模型、实现四角点 PnP 或接入真实相机。

**验收**：单车误检率不能明显上升；多车跨车配对必须低于隐藏阈值；遮挡期间不能持续输出完整后车装甲板。

## F2：补齐跟踪器的丢失、重捕获和误检处理

**比赛情景**：目标被前车挡住 0.5 秒，画面里只剩两个误检灯条；目标重新出现时位置已经变化。旧程序要么马上跳到误检，要么永久保持旧位置。

**代码入口**：`src/f2_tracker.hpp`、`src/f2_baseline.hpp`。

**输入**：`F2_observations.csv`。同一帧可能有多个匿名候选，不能依赖候选 ID。

**要求**：在已有 `BaselineReacquisitionTracker` 的基础上实现或修正 `TRACKING -> TEMP_LOST -> REACQUIRED/LOST` 状态过程：短丢失期间允许有限预测；误检不能立即抢锁；重捕获后要更新位置和速度；长期没有目标必须释放轨迹。

**不要求**：实现 Kalman/EKF、写检测器或接入相机。一个基于位置和时间戳的状态机即可完成题目。

**验收**：报告首次锁定帧、误检切换次数、重捕获帧和最终释放帧；隐藏序列会改变误检位置和丢失窗口。

## F3：把多目标选择器改成带锁定滞回的目标管理

**比赛情景**：两辆敌车在准星附近交替占据更高分数，友军车距离更近，操作手中途指定目标。旧程序每帧按“距离最近”切换，准星横跳并可能锁到友军。

**代码入口**：`src/f3_target_manager.hpp`、`src/f3_baseline.hpp`；可增加独立纯函数测试，不要求接相机。

**输入**：`F3_target_snapshots.jsonl`。这是连续时间序列，不是互不相关的单题；其中包含短暂分数反超、持续反超、短时遮挡、友军竞争、有效/无效操作手指令和全目标过期阶段。

**最低行为契约**：在每帧都会切换的基线之上，先过滤友军、不可见和过期目标；新目标连续明显占优后才切换；当前目标短时丢失时进入 `TEMP_LOST` 并禁火；超过保持窗口才释放；非法操作手指令不能锁友军。

**不要求**：修改检测或跟踪，也不要求神经网络。输入已经是目标快照，重点是状态、滞回和安全决策。

**验收**：统计切换次数、错误友军锁定、短反超造成的误切换、丢失后的释放时刻和重捕获时刻。输出必须带 `selected_id`、状态和原因。

## F4：修正弹道模块的边界和输入契约

**比赛情景**：弹速反馈偶尔为 0、NaN 或突然变化；目标在近距离、高低落差和最大射程附近出现。旧程序在无解时仍把旧角度发给云台。

**代码入口**：`src/f4_ballistic_solver.hpp`、`src/f4_baseline.hpp`。

**输入**：`F4_ballistic_cases.jsonl`。

**要求**：在已有平抛近似基线之上，明确处理无效距离、高度差、弹速、判别式无解和极端仰角；低弹道解和飞行时间的单位必须写清楚；无解时必须让上层进入禁火或明确降级状态。

**不要求**：建立完整空气阻力模型、接云台或改串口协议。可以只改这个纯函数和测试。

**验收**：公开案例和隐藏边界案例均不能输出 NaN/Inf；有效案例的正向回代误差在题面阈值内；无解案例不能沿用上一帧旧解。

## F5：把端到端时延接入瞄准预测

**比赛情景**：相机、视觉处理、串口和弹丸飞行各有延迟。目标在高速横移，旧程序只加一个固定延时，命中点总是落在目标后方。

**代码入口**：`src/f5_latency_predictor.hpp`、`src/f5_baseline.hpp`。

**输入**：`F5_latency_sequence.csv`。

**要求**：在已有常速度基线之上，区分观测时刻、当前处理时刻、发送时刻和命中时刻；不能使用未来真值；处理时延变化、历史不足、时间戳不连续和速度突变；输出预测时长、补偿后位置和 stale 状态。

**不要求**：实现相机线程、串口发送、弹丸模型或完整跟踪器。题目只考查时间语义和一个可测试的预测函数。

**验收**：必须给出零补偿、固定补偿和改进方案的对照误差；隐藏序列会改变时延阶段和运动模式。

## F6：给运行时加上可复现的故障复盘能力

**比赛情景**：比赛中出现检测掉帧、时间戳倒退、跟踪状态没有清零却继续开火。只看最终“没打中”无法定位是感知、跟踪还是时序问题。

**代码入口**：`src/f6_replay_analyzer.hpp`、`src/f6_baseline.hpp`。

**输入**：`F6_detections.jsonl`、`F6_tracking.jsonl`、`F6_commands.jsonl`、`F6_public_issue_times.json`。

**要求**：在已有 JSONL 基线检查器之上，按 `timestamp/frame_id` 对齐日志，识别掉帧、乱序、目标状态与开火命令不一致、丢失期间继续开火等问题；至少新增一个可自动运行的复盘检查器或单元测试。

**不要求**：设计新的日志格式、接入运行时系统或使用第三方大数据框架。候选人只需读取给定 JSONL 并输出结构化 `ReplayIssue`。

**验收**：报告每个问题的时间、涉及模块、证据字段和安全影响；同一日志重复运行结果必须一致，日志缺行不能导致程序崩溃。
